Technical atlas of the Quansheng UV-K5 V3 and UV-K1

Revision: 26-10-2026. Hardware, communications, flashing, and development knowledge base for the UV-K5 V3 and its twin, the UV-K1. Pins, memories, and protocols come from the open-source code currently running on these radios (F4HWN V3, Apache-2.0) and the armel teardown, not assumptions. For step-by-step radio setup, use the getting started from 0 to 100%.

Versions and how to identify them

Firmware for one version does not work on another: the microcontroller is different, and the image will not start or will leave the radio without a display.

VersionMCUData memoryUSB-CReference open firmware
V1 (UV-K5, K5(8), K6, 5R Plus)DP32G030, 48 MHz, 64 KB8 KB I2C EEPROM (expandable)Charging onlyarmel/uv-k5-firmware-custom
V2PY32F030 / PY32G030I2C EEPROMCharging onlymuzkr/uv-k5-firmware-custom
V3 and UV-K1PY32F071, 72 MHz, 128 KB2 MB PY25Q16 SPI FlashCharging and programmingarmel/uv-k1-k5v3-firmware-custom
  • Sticker under the battery: “V2” or “V3.” If unmarked, it is usually V1, but the ARDF manual warns of V3 labels on V2 hardware: this is not conclusive.
  • USB-C appears as a serial port when connected to a PC: V3/K1.
  • Bootloader version (power on while holding PTT): UV-K5 V3 reports 7.00.07; UV-K1 7.02.02 or 7.03.0x. UV-K5(8) V3 radios with 7.0.11 are reported in groups: if you see another number, check before flashing.
  • K1 and K5 V3 share a board (silkscreen K1-V5.0) and firmware. In factory Flash, only the second line of the startup message differs (0x007030).
  • A V3 .bin begins with its vector table: word 0 = stack in SRAM (0x2000xxxx), word 1 = reset at 0x0800xxxx with bit 0 set to 1. A V1 binary has reset near 0x000000xx.

Architecture

The PY32F071 controls everything: it programs BK4829 registers on each change of frequency, mode, filter, or power; reads the S-meter; and manages audio, display, keypad, and memory.

Internal memory

  • Bootloader 0x08000000-0x080027FF (10 KB), never overwritten by DFU.
  • Application from 0x08002800, maximum 0x1D800 bytes (Core/py32f071xb.ld).
  • 256-byte erase pages; 16 KB SRAM.

Factory firmware stores voice at 0x100000-0x196FFF, the same area used by F4HWN. To return to factory firmware, use the guided restoration in UV Studio, which rebuilds that area without touching calibration.

Logical EEPROM map

eeprom_compat.c translates 16-bit EEPROM addresses to SPI Flash to reuse V1 code and CHIRP drivers. Addresses outside the table read as 0xFF.

This is the F4HWN map. Factory firmware, Karina, IJV, and Matoz use another: a CHIRP driver only works with the firmware it was written for.

Calibration

  • Each radio has its own calibration at 0x010000. It is not interchangeable: “Karina calibrations” or those from another unit were calculated for a different radio.
  • Back up before flashing with UV Studio (“dump calib”) or this website's read function; K5Tool-bin extracts values from a dump. Examples of 512-byte dumps are in k1-teardown/openocd.
  • F4HWN commands reject writes to this sector.

Serial programming protocol

The same over the Kenwood jack or USB-C: 38400 baud 8N1, inherited from V1.

XOR obfuscation key (index i mod 16): 16 6C 14 E6 2E 91 0D 40 21 35 D5 40 13 03 E9 80. CRC-16 XMODEM: polynomial 0x1021, initial value 0, over type, size, and data before obfuscation. In replies, the radio pads the CRC with clave[n] ^ 0xFF. A robust reader requires consistent header, footer, and length and only logs CRC mismatches.

F4HWN Fusion extensions: 0x0720-0x0729 slots and banks, 0x0730-0x0737 overlaid apps, 0x0738 physical Flash read, 0x073A/0x073C sector erase and programming (reject calibration), 0x073E CRC-32 of a range. Slot 0 cannot be erased or overwritten. K5Viewer injects keys with AA 55 03|04 <tecla>; PTT is locked.

Bootloader and flashing

With the radio off, hold PTT and power on: LED on, display off. The factory bootloader listens over USB-C and the jack using the same frames.

Bricohams Studio and UV Studio accept only bootloader 7.00.07 for UV-K5 V3 and 7.02.02/7.03.0x for UV-K1, and validate .bin vectors before opening the port. A V1 image can be “flashed” but will not boot.

ToolUse
UV StudioFlashing, multiboot, calibration dump, factory restoration
Bricohams StudioChannels, settings, slots, and main firmware
Multi-UVToolsMulti-model web flasher
MotoAlternative UF2 bootloader: USB “MOTO” drive and drag .uf2. Risky, no serial commands

*.packed.bin files are for the official updater; flat .bin files are for the open tools.

SWD and recovery

If the bootloader is damaged, SWD (PA13 SWDIO, PA14 SWCLK) with an ST-Link is the only option. The PY32 is treated as an STM32F0 with a different TAP ID:

openocd -f interface/stlink.cfg -c "set CPUTAPID 0x0bc11477" -f target/stm32f0x.cfg -c "adapter speed 1000" -c "init; reset halt; dump_image K1_PY32F071.bin 0x08000000 0x00020000; shutdown"

Do not flash a complete external Flash image with a programmer: you would erase calibration. The “Factory_Reconstructed” images from k1-teardown are for guided restoration with UV Studio.

Build firmware

Recommended base: armel/uv-k1-k5v3-firmware-custom, which already handles PY32 startup, Puya HAL, SPI Flash, BK4829, USB, and protocol.

git clone --depth 1 https://github.com/armel/uv-k1-k5v3-firmware-custom
cd uv-k1-k5v3-firmware-custom
./compile-firmware.sh Fusion
./compile-firmware.sh Fusion -DENABLE_VOX=OFF
./compile-firmware.sh All

The container uses ARM GNU Toolchain 13.3.rel1, CMake, and Ninja. Presets: Custom, Fusion, FieldOps, Transfer, Labs, and Max. Output in build/<Preset>.

Karina and closed-source code

Karina is closed-source (see Karina). According to Russian groups, it continues fagci-mod v1.2.1 (Apache-2.0, which permits closed derivatives). To reproduce its features cleanly: describe them from the manual and changelog, start from F4HWN V3 and the spectrum code in fagci-mod and PUNKTRACKER 2.5 (Apache-2.0, V1). fagci/s0v4, hawk5, and k1-fw have no license: they may be read, not copied. Do not decompile Karina's binary to reconstruct its source.
