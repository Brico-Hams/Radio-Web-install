Karina: technical case file and limits of a Bricohams derivative

Inspection date: 2026-10-25.

1. Status and scope

New evidence from 2026-10-25: the Dim0s link supplied afterward contains another Karina package for V3 and UV-K1, with PY32 vectors. This case file describes the local V1 package, not all existing Karina variants. The Karina V3 and Dim0s pack report documents the download, inventory, and hashes. Compatibility with Armel slots has not been demonstrated, and no sources/MIT notice were found in that ZIP.

This document describes evidence from the local Karina-2026.08.21 K5V1 (Fw+Cal+Instr+K5prog+Rolling) package and compares it with the open references listed as references. It is not recovered source code, a complete translation of its manuals, or firmware certification. No Bricohams Karina binary has been created, the bootloader has not been modified, no radio has been flashed, and V1 multiboot has not been tested. An independent Bricohams V3 edition based on F4HWN has been built, described in BRICOHAMS-FIRMWARE.md; it does not include Karina code and is not intended to be its port.

Blocker for deriving Karina: the package contains no C or assembler sources, linker, Makefile, or firmware license. Having a .bin does not provide its build project or allow assigning it another project's license. The three Python files are CHIRP drivers, not processor firmware.

The MIT license attribution for the firmware remains an unverified claim; the component, rights holder, and text or verifiable source have not been identified. No such notice was found in the inspected package, and the licenses of the drivers or F4HWN are not changed by it. Even if MIT is confirmed for Karina, its source project is still required for a rebuild.

Without open source, reconstruction remains an independent implementation based on documented behavior. Availability of Karina source is no longer maintained as a prerequisite for writing new functions. It is still impossible to promise a Karina rebuild or 100% equivalence without implementation and testing. The first custom ARDF core, its contract, and pending integration points are described in Bricohams. Three independent images are now built for V3 slots: ARDF with cycles, Satellites with manual RX Doppler, and Spectrum with 128 points, averaging, peak hold, and eight RAM session presets, plus its own receive-only VFO-PRO capture. Capture supports step tuning, numeric RX entry, audio, and adjustments to the documented R13 RX fields while preserving other bits. It supports centering windows and cycling through RAM presets, with a temporary blacklist of 16 exact frequencies and optional FM CTCSS/DCS search through the upstream detector, pending RF validation. It does not edit calibration, save tones, or transmit. Satellites does not implement TLE/SGP4 or autonomous tracking. During the initial inspection none had been flashed. On 2026-10-26 CRCs of the Bricohams slots in external Flash were subsequently verified, as recorded in the Quansheng guide. This does not validate ARDF/Satellite/Spectrum startup, Karina equivalence, or RF. Splitting by function does not mean all Karina modules have been recreated. Spectrum presets can now be exported/imported over USB/UART in BHSP files, with validation and reread; they do not persist internally in EEPROM. The Satellite image has experimental CAT RX and orbital tracking from the web, not within the MCU. ARDF can export a summary of manual observations, without GPS. Functions and behaviors remain to be reconstructed and verified.

Documenting observed functions and preparing a custom implementation on an open base are possible. That implementation must not be announced as recompiled Karina or claimed equivalent without verification.

Source search (2026-10-26). No public Karina source code was found in the sources consulted; this does not prove it does not exist. The Dim0s pack describes it as closed firmware with no repository, and no sources were located in the reviewed Spanish- and Russian-language Telegram groups. Sources were also not located in searches conducted on GitHub, Codeberg, GitLab, Gitee, GitFlic, or GitVerse. According to the Russian group, Karina continues fagci-mod v1.2.1 (Apache-2.0, which permits closed derivatives) and shares spectrum code with PUNKTRACKER 2.5 (Apache-2.0, V1). Those are the open bases for reimplementing its functions; fagci/s0v4, hawk5, and k1-fw have no license and are not copied. The Karina binary is not decompiled. V3 hardware and protocols are in the technical atlas.

2. Method and evidence sources

  • Recursive inventory of the supplied folder, without running EXE files, drivers, or binaries.
  • SHA-256 and inspection of the images' initial vectors.
  • Text extraction from five PDFs, 102 pages total, using PDF.js in an isolated tools directory, outside the web dependencies.
  • Review of the README files, Makefile, linker, and license for open references.
  • Comparison of local images with the PY32 connector checks.

The PDFs produced font warnings during extraction. Diagrams, stable/test version colors, and screenshots have not been visually verified page by page. Therefore no stability is inferred from a missing color, and the inventory is not considered an exhaustive description of the internal implementation. The summaries below are original and do not reproduce the complete manuals.

4. Hardware and memory: do not confuse V1 and V3

The main manual's cover identifies UV-K5, UV-K5+, UV-K5(8), and UV-K6 V1. The radio previously described by the user was a UV-K5 V3.

FamilyRelevant baseConsequence
UV-K5 V1DP32G030 ecosystem / OneOfEleven referenceDifferent image and map; this website does not support V3 slots
UV-K5 V3 / UV-K1F4HWN PY32F071 in Multiboot/Fusion61Existing connector for slots 1-4 and protected Main

v1_210826_2.bin reads SP=0x20003FF0 and Reset=0x0000010B. The RAW files 16.10fw_7.bin and 30.07fw_2.bin show the same vectors. The V3 connector expects a Thumb reset within the application starting at 0x08002800. Karina V1 does not pass that check.

The inspected OneOfEleven linker declares 60 KiB of FLASH and 16 KiB of RAM. The 61412-byte Karina image leaves only 28 bytes compared with 60 KiB; this is a size comparison against that reference, not an internal Karina map. It does not demonstrate space for another firmware or a bootloader. The 18 additional bytes in .packed.bin files are not usable free space.

The Karina manual cover warns that it does not support Si4732 and that expanded M24M01/M24M02 memories are not used as expanded memory. There is no evidence in the package of firmware slots compatible with F4HWN V3 Multiboot.

5. Functional documentation for Karina

The functions in this section come from the manual text, not from hardware tests or inspection of implementation code.

5.1. Display and status (main manual, pages 3-4)

  • VFO/channel display and last active receiver.
  • Power-saving, keypad-lock, and function-mode indicators.
  • Dual watch, CTCSS/DCS information, and membership in scan lists.
  • Battery, signal meter, names, and frequency.
  • AM/FM/SSB mode indication; the SSB label does not demonstrate receiver performance equivalent to a dedicated SSB radio.

5.2. Menus and persistence (pages 5-9)

  • SQL, tuning step, power, offset, tones, and bandwidth.
  • Busy-channel lock, memory save, and name style.
  • Power saving, VOX, dual watch, and scan behavior.
  • RX/TX audio settings and specific filtering functions.
  • Hidden menus and advanced parameters: they must be documented against sources before being exposed in a Bricohams build.

The manual distinguishes VFO-, band-, and memory-specific parameters, and explains that some channel changes persist only after an explicit save. A port must not confuse temporary settings with persisted data.

5.3. Keypad, listening, and scanning (pages 10-16)

  • Short, long, and function-key combinations.
  • VFO/MR switching, copying settings, and frequency entry.
  • Scanning and functions assignable to side keys.
  • The manual warns of possible problems assigning NONE to FN1/FN2 with external tools; driver compatibility must be verified.

The manual also describes automatic TX and randomization functions. Their presence in the documentation does not make them requirements for the new firmware. They are not automated, and sequences for interfering with services are not provided here. An initial derivative should preserve legal limits and keep automatic TX off.

5.4. Spectrum analyzer (pages 17-24)

  • Spectrum display and activity visualization.
  • Tuning, active-frequency selection, and relationship to memories.
  • Free-entry ranges and presets.
  • Multipreset and scan parameters.
  • Detailed view called VFO-PRO.
  • Gain parameters and receiver registers, including LNA/PGA.
  • The manual states that certain parameters may be written to calibration when exiting the spectrum analyzer: do not treat them as harmless visual controls.

Algorithms, filters, timings, limits, and register mappings have not been verified in Karina sources. It is not correct to implement assumed offsets based on screenshots or text.

5.5. Troubleshooting and evolution (pages 25-29 and separate history)

The manual covers usage and configuration problems; the history lists changes to reception, squelch, power saving, scanning, subtones, and spectrum. The 2026-08-21 entry mentions a reception lock fix associated with a mode described as Roger 5 and references 29.01.26calib_sql.bin. This does not certify that the file is suitable for another unit.

The history spans versions from 2023-2026. Its stable/test color coding is not reliably preserved in text extraction. It is not claimed that all binaries in the folder are stable.

6. CHIRP: what is present and what it does not prove

Python fileObservation
f4hwn.chirp.driver.v2.8.1+Karina-5.pyDeclared UV-K5/1 model, based on Egzumer/F4HWN/Karina
Chirp dr Karina-by_M2Boo-K1-2.pyDeclared UV-K5V3/K1 model, despite being in the V1 package
chirp_uvk5_fagci_osfw.pyUV-K5/Fagci driver; does not demonstrate compatibility with the latest Karina image

The driver headers indicate GPL v2 or later. That license applies to those files; it does not establish a license for the attached closed firmware. The drivers declare 38400 baud and 0x2000 bytes of data memory. The two F4HWN/Karina derivatives declare data writes up to 0x1D00 and calibration from 0x1E00. These are driver declarations, not proof that all three work with every revision.

These Python files were not imported or run. A CHIRP module executes code on the PC; it must be reviewed and selected for the exact model, firmware, and version. The presence of a V3 driver does not turn the V1 binary into V3 firmware.

Each entry shows its status or reason for being blocked. Length, PY32 vectors, F4HWN v6.x identification, and excluded variant names are checked. SHA-256 is calculated locally. A version string and correct vectors do not certify authenticity, correspondence with source, or physical compatibility. The local build is not presented as signed by Armel.

ARDFv05 contains sources, but no completed ARDF image was found in its inspected firmware directories; archive contains earlier Fusion images and stock images. No supposed ARDF image inferred from a folder name is offered. ARDF catalog releases remain download only.

Preparing an image does not write anything. Installation still requires a compatible connection, verified full backup, slot 1-4, confirmation, and final CRC. Main remains protected. Karina V1 is also blocked when given a false F4HWN name because its vectors do not meet the PY32 format.

9. Contract required for a reproducible Bricohams version

This is pending work, not functionality Karina already has:

  1. Obtain Karina's exact sources, license, dependencies, and tools, or approve an alternative open base and record its differences.
  2. Select hardware separately. V1 and V3 require different projects/profiles and binaries. For the user's existing slots, the applicable base is PY32, not the package's V1 binary.
  3. Reproduce the build unchanged before modifying it; record commit, toolchain, options, map, and hashes. Do not invent an upstream SHA.
  4. Create minimal profiles with dependencies and FLASH/RAM budgets. Reject unknown options and combinations that do not fit.
  5. Preserve upstream identity/license and add Bricohams branding without artificially altering a string to pass slot validation.
  6. Deliver .bin, map, size report, build-info.json, and SHA256SUMS covering both firmware and metadata. Do not confuse a hash with a signature.
  7. For V3, test startup, CFG switching, own calibration, backup, recovery, and slots against F4HWN. For V1, first demonstrate physical storage support and a bootloader recovery strategy.
  8. Publish only after bench testing; document RF limits and do not automatically enable transmissions outside permitted bands.

The website already has an options form for the Brico-Hams/bricohams-firmware workflow; it is not a Karina compiler. This task did not run that workflow. An independent local builder has been added for F4HWN v6.1.0 and used to generate Bricohams Fusion and Labs editions. The rest of this section remains a requirement for deriving Karina, not a claim that Karina functions have been reimplemented in those binaries.

10. Recovery and operational limitations

The rollback readme.txt describes operations that erase data. They are not automated and should not be applied because of a USB failure. Before any migration, original unit backups, hardware identification, and a tested recovery procedure are required.

The website maintains write barriers. The original package files and the Multiboot folder have not been touched. PDFs, EXE files, calibration files, or Karina firmware are not redistributed.
