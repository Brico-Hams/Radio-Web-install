Bricohams V3: Local Modular Build

Identity and Scope

BETA, undergoing validation and testing. New builds declare stability: "beta" and the validation scope in build-info.json, covered by SHA256SUMS. hardwareTested: false is retained until that exact binary has been tested. A real radio read using F4HWN v6.0.0 does not validate this Bricohams firmware. The web PRO Mode reduces confirmations; it does not change modules, licenses, or firmware protections.

Edition derived from the open F4HWN base for UV-K5 V3 / UV-K1 PY32. It is not Karina, does not support UV-K5 V1, and does not add its own bootloader. It reuses the upstream multiboot and retains its protocol identity, F4HWN v6.1.0. The on-screen edition becomes Bricohams through a CMake variable, without patching the binary.

This open base was chosen to continue on the V3 hardware and its slots. The limitations that prevent deriving Karina are documented in KARINA.md. Its algorithms, menus, and drivers have not been ported.

Build on Demand

Independent Line: Bricohams App Platform

firmware/platform starts a line distinct from the F4HWN application. It contains an in-memory package validator/loader, an initial service contract, and diagnostic and blocks apps written in C and tested on desktop. It now includes a buildable experimental resident with PY32 startup and LCD/keyboard glue. It has not been verified to boot on the radio. It is not a validated, installable replacement for Labs or a complete SDK. Its connection to physical USB, Flash, LCD, keyboard, or RF has not been tested.

The experimental BHA1 format is not FAP1 and must not be installed with the existing web app loader. Integers are little-endian:

OffsetBytesField
04Magic ASCII BHA1
44Header size, 64
84API version, 2
124Architecture, 1 = Cortex-M Thumb
164Code size, even, 2..4096
204Initialized data, 0..1024
244BSS, zeroed when loaded
284Even entry offset within code, without Thumb bit
324Requested capabilities: display 1, keyboard 2, RX 4

Code and data follow, with no trailing bytes. Code, data, and BSS together must not exceed 4096 bytes: this is an initial budget, not a measurement of the resident firmware. The loader validates everything before modifying the destination buffer, copies code/data, and zeros BSS. It does not call the code, resolve relocations, or know the final link address. The output descriptor must be independent of the input and destination buffers; memory and its lifetime are the caller's responsibility.

CRCs detect corruption; they do not authenticate the author. Capabilities are an admission filter, not a sandbox: native code on an unisolated MCU can access peripherals directly. Do not execute untrusted code or claim calibration isolation based on this filter. This component has no TX API or Flash writing.

The resident's boot, LCD, and keyboard still need validation on PY32; Flash/USB/RF drivers, real stack and timing measurements, physical transactional installation, recovery, and full hardware integration of the apps remain incomplete. Doom has not been implemented. This format is provisional and does not demonstrate physical operation of the apps. The previous profile line is not being replaced.

First App: Display Diagnostics

bh_api.h defines an experimental C ABI version 2 with version, size, context, and callbacks to clear, write text, and present the display, plus a private app state buffer and its size. It receives START, KEY, TICK, and STOP events. Keys are platform identifiers, not UART codes: EXIT has value 1. The app returns continue, exit, or an explicit error; if a callback fails, it requests no further display services.

diagnostics.c displays four Bricohams lines and accepts EXIT/STOP without writing to RF or storage. Its desktop execution uses simulated services; version/size, missing callbacks, and errors at each stage are checked. This does not execute ARM instructions on the radio.

It requires the ARM tools already used by the project and a new destination. It produces ELF, a code BIN, diagnostics.bha, a license, and a manifest with SHA-256 hashes of the sources and package. Second App: Blocks

blocks.c implements an original four-cell piece game with seven shapes, rotation without wall kicks, collisions, falling, locking, line clearing, game over, and restart. It uses no code, images, sounds, or data from Tetris or Doom. The text board is 10 columns by 6 rows to test the current callbacks; it is not a final graphical LCD port.

LEFT/RIGHT move, ROTATE turns, DOWN drops one step, DROP locks the piece, RESTART starts over, and EXIT exits. Each TICK drops one step: the core must define the cadence, independently of loop speed. The pseudorandom sequence is deterministic and resets on START/RESTART. Lines are counted in state but are not yet displayed as a score.

The core must provide the state in aligned memory, zeroed before the first event and exclusive to this app. The manifest reserves an external budget of 256 bytes; this is not package BSS. The API 2 contract includes this buffer and replaces the initial API 1. The loader rejects API 1 packages: distinct binary contracts are not silently mixed.

The app compiles for Cortex-M0+ without a C library or division helpers: 940 bytes per package (64-byte header, 876 bytes of code/constants). Desktop tests verify movement, rotation, line clearing, game over, restart, service errors, and 10000 events with undefined-behavior checks. The C loader also validates and copies the real ARM package. That ARM code has not been run on the radio. The experimental resident includes a launcher, but not an external package installer.

Portable Launcher

bh_launcher.c manages one native app at a time with an exclusive, aligned 256-byte buffer. Initialize a new instance and keep it at the same address for its entire lifetime: the contract contains a pointer to its own memory. Do not copy instances or reinitialize them while an app is running.

START is sent exclusively by bh_launcher_start; the dispatcher accepts KEY, TICK, and STOP. When switching apps, STOP is sent to the previous one; exit or error releases the app and clears all its state. A STOP error prevents starting the next app. Reentrant start/stop/dispatch calls during a callback are rejected. Ticks must be delivered serially from the main loop; this is not an interrupt-safe API.

The launcher invokes already-linked C functions for desktop tests. It does not turn an ARM package address into a function or execute BHA1 on the PC. MCU execution bridging, Flash installation, drivers, an LCD menu, and recovery are still missing. This is a tested portable lifecycle, not a bootable resident launcher or a sandbox.

Persistent Installation with Two Banks

bh_store.c implements portable storage for one package and its previous version in two abstract 8192-byte banks. It is not yet a multi-app catalog. The driver must provide read, write, and erase operations exclusively for those banks; no radio Flash address has been assigned and the F4HWN map is not reused.

Before erasing, the complete BHA1 API 2 package is validated and the previous version is queried. Only the inactive bank is erased, then read-back verifies that every byte is 0xff, including the confirmation marker: an erase ACK without an actual erase is rejected before programming. The package is written in chunks that do not cross 128-byte pages, and each chunk is read back. The BHS1 header contains version, generation, length, and package CRC; it is read back before writing DONE as the final confirmation. The header and package are validated again after confirmation. The previous bank is not erased at the end.

Reading selects the most recent valid generation and can recover the previous one if the new one is incomplete or corrupt. If neither is valid but a confirmed corrupt bank exists, an error is reported and it is not automatically overwritten. A driver error aborts without simulating success. Equal generations are ambiguous and rejected; when uint32_t is exhausted, a new installation is blocked rather than allowing wraparound.

The caller must provide scratch space independent of the package of at least 4160 bytes and serialize all operations. This maximum includes a 64-byte header and 4096 bytes of combined code/data: the individual maximum code and data sizes are not added because the BHA1 contract limits total RAM to 4096. This reduces scratch by 1024 bytes compared with the initial allocation without reducing the set of valid packages. Tests cover both 4096-byte code and 3072-byte code plus 1024-byte data, and rejection without I/O when scratch is one byte too small. There is no heap or internal full-bank buffer. After a final write/read-back error, installation may already be confirmed: query again before retrying; do not assume rollback.

bh_store_load connects bank selection to validated loading into RAM: it copies code/data and clears BSS, without jumping to the entry point. Scratch and RAM must be independent, as must the output descriptor. An undersized destination returns BH_STORE_NO_SPACE; errors do not modify RAM or the descriptor. The caller must reserve the real link address before execution; this helper does not validate addresses or turn bytes into a function.

Tests with simulated NOR cover 322 interruptions/read, write, and erase failures during first installation and update, including partial writes, false write/erase ACKs, corruption, maximum-size packages, equal generations, alternation, and generation exhaustion. Each interruption during an update verifies that the previous bank remains unchanged. Loading code/data/BSS and RAM preservation on errors are also tested. This does not test power-loss tolerance or atomicity of the real chip. SPI/Flash driver, sector reservation, USB installer, and integration with the resident launcher remain incomplete.

Experimental BHT1 Receiver and Transfer Client

bh_transfer.c implements the receiver state machine, without a serial/USB driver. scripts/platform-transfer.cjs encodes requests, validates responses, and provides uploadPackage(exchange, bytes, session), where exchange must deliver a complete frame and return exactly its response. It does not open ports or provide installation in the current web app.

Each request has a 24-byte header and up to 128 bytes of payload. All integers are little-endian u32:

OffsetField
0Magic BHT1
4Operation: BEGIN 1, DATA 2, COMMIT 3, ABORT 4, STATUS 5
8Nonzero session ID, chosen by the client
12Offset in package for DATA; zero for other operations
16Payload length
20CRC-32 of header and payload, with this field set to zero

BEGIN contains two u32 values: total length (66..4160) and CRC-32 of the entire BHA1. DATA sends contiguous blocks of 1..128 bytes. A duplicate block is accepted only if it exactly matches bytes already received and does not advance the offset twice; gaps and partial overlaps are rejected. A duplicate BEGIN with the same session/length/CRC retains progress. A different session cannot interrupt an active transfer. ABORT cancels without calling the installer; STATUS queries without extending the timeout. The transfer expires 30000 ms after BEGIN or the last valid DATA, using unsigned differences to handle wraparound. An expired or cancelled session requires a new ID.

COMMIT requires all bytes, a correct total CRC, and BHA1/API/capability validation before invoking the installer callback. A duplicate COMMIT does not invoke it again, whether it succeeded or returned an error: a write error may mean Flash was already confirmed. The client does not automatically retry a COMMIT whose response is lost; it must query STATUS and storage before deciding on a new operation.

The BHR1 response is 32 bytes: magic, operation, session, result, bytes received, state, installer result (i32), and CRC of the first 28 bytes. Results: OK 0, BAD_FRAME 1, BAD_SESSION 2, BUSY 3, BAD_OFFSET 4, INCOMPLETE 5, BAD_PACKAGE 6, INSTALL_ERROR 7, EXPIRED 8, BAD_STATE 9. States: IDLE 0, RECEIVING 1, DONE 2, FAILED 3, CANCELLED 4, TIMED_OUT 5. The client rejects an incorrect CRC, session, operation, state, or offset ACK.

The caller must serialize calls, keep the instance and staging alive, and provide independent buffers for the instance, staging, frame, and response. 4160 bytes of staging are required. The callback receives that staging only during COMMIT and must not modify or retain it. A reentrant call returns BUSY without producing a response. The future physical transport must limit waits, report disconnections, and implement flow control. The transfer API receives complete frames; assembling an arbitrarily fragmented stream belongs to bh_stream.c, described below. CRCs and the session ID do not authenticate the sender.

bh_stream.c consumes one byte per call, recognizes BHT1 magic and a length limited to 128 bytes, and checks the CRC before passing the frame to the receiver. It requires no length prefix or additional delimiters. It tolerates fragmented or concatenated frames. It searches for magic again after noise, an impossible length, or an incorrect CRC; magic inside a valid payload is not interpreted as a second request. It returns explicit framing errors, and only BH_STREAM_REPLY authorizes sending its BHR1 buffer. The caller must report or log these errors, not simulate success.

A partial frame expires after 1000 ms without new bytes, using unsigned differences to tolerate wraparound. bh_stream_poll allows checking this timeout without receiving another byte. A timeout discards only the partial frame; it does not cancel the transfer session or alter the previous bank. The driver must report a disconnection and decide whether to allow resuming the existing session. Calls and buffers must be serialized; the installer callback must not reenter the stream. There is no heap: the assembly buffer occupies 152 bytes, in addition to the structure, response, staging, and validator temporary memory.

The desktop integration sends the raw BHT1 stream from JS to the C receiver over pipes, installs to simulated NOR, and validates the subsequent RAM load; it covers two generations, a maximum-size package, and repeats without reinstalling, adding noise before each frame. The length prefix used only by the first harness has been removed. The same test with the real ARM packages for Diagnostics and Blocks completes 34 JS/C exchanges, including cancellation and rejection of an incorrect total CRC without replacing the active bank. The C test also checks 10000 malformed frames without changing the session or calling the installer. The stream tests all cut points of a STATUS frame, concatenated frames, maximum payload, nested magic, recovery after corruption, timeout across wraparound, and 100000 noise bytes. The receiver and stream also compile for Cortex-M0+. They are not linked to the resident and do not write physical Flash: staging, scratch, app RAM, and stack must be budgeted together before integration; buffers cannot simply be added without checking the 16 KiB limit.

With the current maximum buffers, staging and scratch total 8320 bytes: they already exceed the 8192 bytes reserved for CORE by 128 bytes, even before structures, framebuffer, or app state. APP and STACK have their own 4096-byte regions; those are not free RAM for these buffers. Reducing scratch removes waste, but does not by itself solve integration. The receiver will not be connected to the resident by simply adding these buffers, nor will the stack be reduced without measurements to hide the excess. Block-based storage/verification or reuse of memory with tested lifetimes and overlaps is needed, while retaining the current contract that prevents package and scratch from overlapping during installation.

The custom startup initializes data/BSS and VTOR. It disables and clears inherited external NVIC interrupts and pending SysTick/PendSV; it then enables only the 1 ms SysTick as a time base. The menu lets the user select Diagnostics/Blocks with UP/DOWN and open with MENU. In Blocks: 4/6 move left/right, MENU rotates, DOWN drops, * drops directly, 0 restarts, and EXIT returns. Three stable keyboard samples 10 ms apart are required; a held key does not repeat and key combinations are not accepted. The shell requests a tick no more than every 500 ms, without catch-up bursts. Game ticks use unsigned time differences to tolerate millisecond counter wrap. The ISR must be serviced before the next millisecond; an app may not mask interrupts. This cannot be enforced for untrusted native code: actual timings must be measured.

ELF, experimental BIN, map, compiler stack reports, BHA1 packages, manifests with SHA-256, and licenses/notices are produced. The builder checks BIN limits, stack/Reset/SysTick vectors against ELF symbols, targets for all remaining vectors, RAM limits, and absence of unresolved symbols. Its tests reject incorrect Thumb vectors, overlapping RAM, and missing symbols without needing the ARM compiler. Individual stack reports do not prove the maximum cumulative stack usage. The shell and renderer are tested on desktop, including ticks at 499/500 ms, time wrap, return to menu, errors, and text limits. The 3x5 renderer is original and includes no fonts or resources from other firmware.

Do not load this BIN with the current web installer or as a multiboot slot. It does not implement F4HWN slot identification/CRC, USB protocol, recovery, or external app installation. The manifest keeps hardwareTested: false and installableWithCurrentWeb: false. The first boot test must be done with a verified full backup and a verified recovery path.

Custom Satellite Core

firmware/bricohams/doppler.c calculates frequency corrections using radial velocity in mm/s. Positive means the satellite is moving away: RX decreases and nominal uplink increases. Frequencies are expressed in 10 Hz units and rounded to the nearest step. The formula matches the classical nonrelativistic model used by the web planner; it does not reproduce a Karina algorithm or enable transmission. The output always declares receive_only=true.

BRICOHAMS_ENABLE_SATELLITE=OFF excludes the library. It validates VHF 136-174/UHF 400-470 for both nominal and corrected frequencies, and radial velocity up to 12 km/s in either direction. Invalid input preserves the previous output and returns an explicit error. It does not generate TLE, UTC time, position, SGP4 passes, or radial velocity: those data must come from a validated predictor. It also does not implement CAT, automatic tracking, or persistence. Tests compare 241 velocities against a double-precision reference, including signs, limits, and rounding within half a unit (5 Hz).

CAT RX Bricohams v1 Implemented

The Satellite-CAT-final-20261025 image measures 113868 bytes RAW, RAM 12384/16384, and Flash 112980/120832. It includes a Bricohams boot logo and an original experimental endpoint, not compatibility with Kenwood/Yaesu CAT protocols or CAT support from other F4HWN editions.

In SAT RX, press 8 with the keyboard unlocked: CAT READY RX. A valid command displays SAT CAT RX. Keys 4/5/6 disable CAT and return control to manual Doppler; 8 disables it and restores the entry nominal RX frequency. Locking the keyboard cancels CAT and returns to nominal RX. Exiting the mode clears CAT state before restoring the VFO through the upstream flow. Reentering requires enabling it again with 8.

Each SET renews a 3000 ms lease. On expiry, nominal RX is applied, any pending SET is discarded, and CAT TIMEOUT is displayed; CAT remains enabled for a new valid command. QUERY, invalid commands, and errors do not renew the lease. A correction from a lost pass is not held indefinitely. The timeout is checked in the RX loop, not an interrupt: it depends on the firmware continuing to execute that loop. It is not a hardware watchdog or a guarantee against a CPU lockup.

The endpoint reuses existing USB CDC/UART frames with obfuscation and CRC; this is not encryption or authentication. It accepts only absolute frequencies in 10 Hz units, within 136-174 or 400-470 MHz inclusive, and applies them only in locally enabled SAT RX. It does not modify channels, tones, power, EEPROM, Flash, or TX. Modulation/bandwidth are those of the entry VFO. Do not use it as transmission control or claim that RF tuning has been measured: confirmation means the RX primitives were invoked.

Little-endian binary contract, private command 0x7B00, response 0x7B01. The upstream Size header expresses data length, excluding the header. No new commands are assigned for unrelated firmware.

Custom Spectrum Presets, Without Writing EEPROM

firmware/bricohams/presets.c defines a 208-byte BHSP v1 container with up to 8 presets: 8-character ASCII name, start frequency, step, points, settling, and samples. Optional CTCSS/DCS RX Search

In FM capture, 9 enables CSS SEARCH...; pressing 9 again disables it. CSS NEEDS FM rejects enabling in other modes without writing RF. R51 is saved before enabling and restored when disabled, returning to sweep with EXIT/5, or exiting the mode. The search primitive may reset the RX path, so R13 gain and R7E AGC registers are preserved and reapplied. Calibration is not written and results are not saved. Changing frequency restarts the search at that frequency; changing gain discards the previous candidate and indication.

Results are ignored during the first 500 ms after tuning/enabling and are queried at most every 250 ms. New Independent ARDF Core

The original implementation is based on documented behavior and binary inspection, without waiting for Karina sources. This does not establish 100% equivalence or turn the F4HWN base into a complete rewrite from scratch.

firmware/bricohams/ardf.c and ardf.h are an independently written C99 core: ARDF or Karina implementations have not been copied. It implements cycles for 1-10 transmitters, no-cycle mode (0), transmitter/phase synchronization, turn-end warning, and gain-index memory by VFO/transmitter with an A/B mask. It does not control the RF chip, TX, speaker, display, keyboard, EEPROM, or calibration.

Contract:

  • bh_ardf_init validates before changing state. Reconfiguration clears gain history. A rejected configuration preserves state.
  • The input clock is monotonic uint32_t milliseconds; rollover between calls is allowed, but backwards jumps or intervals of 2^32 ms or more are not. The adapter must convert the radio's tick base.
  • correction_ppm from -50000 to 50000 changes clock advancement; positive speeds it up. It is not another firmware's ClkCor value or an RF oscillator adjustment. Fractions are retained between updates.
  • Duration is 1000 to 999990 ms, warning is 0 to 30000 ms and cannot exceed the turn. These are limits of this implementation, not binary equivalence.
  • max_gain_index must come from an RF table validated for the hardware; the core does not assume an index represents 5 dB.
  • Gain lookup returns available=false if there is no history; in that case the output index is unchanged. The caller must check the result, not turn it into a default RF adjustment.
  • Functions return explicit errors; a future adapter must report them. Do not call concurrently from interrupts and UI.
  • BRICOHAMS_ENABLE_ARDF=OFF excludes the entire library at build time. This is a build selection, not dynamic module loading.

New Independent Spectrum Acquisition Core

firmware/bricohams/spectrum.c and spectrum.h implement an original C99 state machine, without copying Karina algorithms. It configures 1 to 128 points, start frequency and step in 10 Hz units, settling of 1-1000 ms, and averaging of 1-16 RSSI samples per point. Each point retains mean level and peak hold; resetting peaks uses current levels. BRICOHAMS_ENABLE_SPECTRUM=OFF excludes this library.

The adapter must request bh_spectrum_frequency, validate the actual band, tune the receiver, and call bh_spectrum_tuned only on success. Samples before settling return NOT_SETTLED and are not included. Tuning is required again after each point, even when there is only one point. frames increments after a sweep completes. Values are raw RSSI, not calibrated dBm; the adapter must ensure a larger value represents a stronger signal.

The clock has the same monotonic 32-bit contract as ARDF; functions are not called concurrently. The adapter determines cadence and takes distinct RF readings: calling repeatedly with the same reading does not create independent samples. The core does not control AGC/LNA/PGA, transmit TX, calculate an FFT, or save presets/calibration.

Tests exercise limits, point changes, exact frequency calculation, averaging, peaks, settling, rollover, 128 points with 16 maximum RSSI samples, and atomic rejection of invalid/overflowing configuration. This is not the Karina analyzer. The spectrum image adapter connects this core to receiver and display within the Beta scope described above; physical validation remains pending.

Provisional Assumptions and Limits

Without answers to the clarifying questions, USB OTG with a programming cable is the planned initial transport. Bluetooth would require a verified adapter and protocol; Bluetooth is not assumed to be built into the radio. A programming serial cable does not imply audio transport: SSTV and Morse need a separately verified audio input/output path. It is not assumed that Android can maintain USB and that audio path on every phone without testing.

CAT is not considered available just because channel read/write exists. First verify the firmware's actual capabilities and, if needed, design a versioned custom protocol with capability query, model-specific validation, acknowledgments, errors, and disconnect recovery. TX, band limits, and backup protections remain in force. Tracking must not enable TX automatically or continue issuing changes after losing the connection or stopping the pass.

Direct LoTW upload remains a goal, not a completed integration. The accepted signing mechanism and secure management of the callsign certificate on Android must be verified. The initial alternative is ADIF for signing with TQSL on a computer; exporting ADIF is not equivalent to uploading it to LoTW. Do not include certificates, keys, or passwords in the repository, diagnostic logs, or exported projects.

The requested term "encriptions" needs clarification: it is not automatically interpreted as encryption of amateur radio communications. Encryption support or its legality is not claimed.

GPS provides the phone's location, not the beacon's. An estimated transmitter location requires sufficient observations/bearings and must show uncertainty; RSSI alone cannot establish an exact location. Tracks and positions are private by default, require explicit permissions, and are not published automatically.
