Validacion integral UV-K5 V3, Android y firmware Bricohams

Autores: Anatol Emilio Lopez Maitchovcow EA5KAO, Diego Roca EA5JEF y Pedro Roca, fundadores y miembros directivos de Bricohams. Informacion: https://bricohams.org y https://bricohams.com.

Revision inicial: 26-10-2026. Auditoria en curso; no es un certificado de funcionamiento ni una revision exhaustiva ya completada. Los avisos y atribuciones de codigo, fotos y documentos de terceros se conservan.

La web publicada no es necesariamente igual al arbol local. Tampoco se deduce el contenido del APK descargable a partir del texto de una guia. No se deben atribuir las pruebas de la base local a la revision publicada ni a un APK sin identificar.

Este dibujo es una representacion funcional propia, no un esquema electrico. No contiene conexiones internas, valores de componentes o niveles de tension inferidos. Los mapas de pines y memoria estan en el atlas.

Niveles de evidencia

  1. Fuente revisada: demuestra la implementacion prevista, no su ejecucion.
  2. Test host/JVM/Robolectric: verifica los escenarios concretos simulados.
  3. Android instrumentado: requiere dispositivo/emulador identificado.
  4. Radio real: requiere version, slot, banco y configuracion identificados.
  5. Medida externa RF/electrica: requiere instrumento, conexion y procedimiento.

Un ACK de escritura no sustituye relectura, persistencia tras reinicio o medida RF. Un test SQLite de escritorio no certifica la memoria del movil. El estado final de cada escenario debe indicar nivel y evidencia; no convertir "no ejecutado" en "correcto".

Hallazgo corregido: CRC de backup Android

QuanshengMemory.verifyFlash solicitaba 0x073E sobre 2097152 bytes de una vez. El comando de referencia limita cada consulta a 4096 bytes. El mock permitia el rango imposible y ocultaba el error. La web ya verificaba por sectores; Android necesitaba la misma correccion.

La correccion local consulta los 512 sectores con direccion/longitud/estado comprobados y compara el CRC de cada sector contra los bytes leidos. Solo devuelve el CRC local total despues de comprobar todos. Un fallo, incluido el ultimo sector 0x1ff000, bloquea el backup y no habilita escritura. No elimina backups existentes, calibra la radio ni escribe sectores.

El mock ahora impone 4096 bytes y comprueba que se solicitan todos los sectores. Se anade prueba de ultimo sector corrupto y rechazo de rango incompleto antes de enviar comandos. Las pruebas host de la base local: 92 correctas tras ampliar limites, cancelacion y pantalla de canales, cero fallos/errores; lint sin errores y 13 avisos. La APK debug se compila, pero esta correccion no esta publicada ni instalada en un movil.

SHA-256 de la APK local reconstruida tras estas correcciones: cd9d3bfd3bfe0405be23995dd906aae63614ec9d38de1a1ff8cea1997156ab25. Este hash reemplaza la reconstruccion local anterior, no identifica la APK publicada ni la instalada.

Tambien se corrige el manifiesto generado por build-android.ps1: ya no declara inexistentes CAT PTT, SSTV TX y programacion de canales que si estan implementados experimentalmente. Esto no convierte esas funciones en certificadas.

Cancelacion y limites del editor Android

Se encontro otro problema durante el seguimiento del ciclo de vida: cerrar la pantalla encolaba el cierre del transporte detras de la tarea activa. Por tanto, una copia o escritura larga podia seguir enviando bloques aunque la interfaz ya declarase la sesion terminada.

La conexion ahora conserva una generacion de sesion y comprueba que sigue activa y en primer plano antes de cada intercambio. Las tareas encoladas tambien comprueban su generacion antes de comenzar. El cierre sigue en el worker para liberar ordenadamente el transporte, pero no habilita nuevos comandos de una operacion cancelada. La respuesta de una orden ya enviada puede quedar pendiente o la orden haberse aplicado: no se promete rollback. Un timeout o cancelacion exige reconexion y respaldo nuevo. Los errores tambien cierran el transporte y eliminan la referencia de memoria, no solo el permiso de backup: pulsar Respaldo de nuevo no reutiliza una conexion invalida. Una prueba de pantalla inyecta un fallo de transporte, comprueba cierre y verifica que el segundo intento no envia mas comandos.

Las pruebas simulan cancelacion despues de ocultar el primer canal: no se envia el siguiente bloque ni se vuelve a mostrar un registro incompleto. Tambien cancelan el backup tras su primer bloque Flash y comprueban que no se consulta el siguiente ni se declara CRC verificado. La lectura Flash fisica exige identificacion y valida rangos mediante resta para evitar desbordamiento de address + length. Se comprueba el ultimo bloque valido. Los casos CRC rechazan longitud de respuesta corta/larga, direccion, longitud de sector o estado incorrectos antes del siguiente sector.

Contactos: alcance y criterios

Los contactos son QSO del libro de guardia, no contactos DMR de la radio ni la agenda telefonica de Android. La radio UV-K5 V3 de este proyecto no es un terminal DMR. No hay integracion con ContactsProvider.

Canales y aislamiento por slot

El editor Android actual edita canales FM existentes: no equivale al CRUD completo de la web ni permite inferir altas/bajas/copia entre slots. No usarlo para prometer gestion de contactos DMR.

Antes de cada ensayo fisico:

  1. Identificar hardware V3/PY32 y firmware exacto, no solo nombre del perfil.
  2. Leer inventario multiboot, etiqueta y CRC; anotar indice interno y etiqueta visible por separado. No escribir suponiendo que "slot 3" es indice 3.
  3. Confirmar banco activo y hacer backup completo verificado en disco.
  4. Elegir un canal de prueba del banco activo sin sustituir datos del usuario.
  5. Probar nombre/RX/TX/CTCSS/DCS/potencia/ancho/TX lock, con TX fisico evitado.
  6. Releer todos los bytes y comparar regiones protegidas y calibracion.
  7. Reiniciar, verificar persistencia; cambiar de slot y comprobar que los otros bancos conservan sus hashes. Restaurar y comprobar el original.
  8. Desconexion, timeout y rechazo de bloque deben cerrar sesion y exigir relectura/backup; un corte no se presenta como transaccion atomica.

La orden de escritura debe ocultar atributos afectados, escribir registros/ nombres y restaurar atributos antes de la relectura. No se modifica el mapa de calibracion ni se restauran datos de otra radio.

CAT en SAT RX y Android

CAT RX es temporal y distinto de escribir canales. F4HWN v6.1 por si solo no garantiza la presencia del modulo CAT Bricohams. Hace falta QUERY valido y capacidades esperadas, con la app SAT RX abierta y CAT habilitado mediante tecla 8. El ensayo inicial no requiere PTT.

Modificaciones de hardware: compatibilidad y limites

La compatibilidad de un mod V1 no se traslada al V3 por compartir carcasa. El MCU, memoria y RF son distintos. La referencia K1 teardown consultada confirma PY32F071, 128 KB Flash, 16 KB SRAM y memoria SPI 2 MB; no demuestra una modificacion concreta en todas las revisiones de placa V3.

No se ha abierto ni modificado la radio durante esta auditoria. No existe evidencia para certificar todas las modificaciones posibles. Los esquemas de conexion interna completos requieren fotos de ambas caras de la placa exacta, trazado de continuidad sin alimentacion y valores/encapsulados identificados por personal cualificado; no se derivan de un diagrama de bloques. En el arbol de trabajo actual, npm test finaliza con 285 pruebas correctas y cero fallos; npm run check tambien termina correctamente.
